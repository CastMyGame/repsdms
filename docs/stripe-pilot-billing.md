# MVP approved-onboarding billing boundary

The product owner disabled new application Checkout initiation for MVP 1. POST /stripe/v1/create-checkout-session returns 503 with a consistent controlled-onboarding message for anonymous visitors and every role. StripeBillingService.createCheckoutSessionUrl also refuses direct calls before reading configuration, saving an intent or invoking Stripe. The original SDK builder remains private and uncalled; there is no environment flag or role that bypasses the restriction. Source inventory found no alternate Session.create/checkout entry point. Registration already uses contact-based approved onboarding; companion frontend changes clarify old checkout return URLs too.

Signed POST /stripe/v1/webhook retains signature validation, successful event-ID dedupe, processing locks, incomplete-work retry and SDK session-retrieval fallback. Verification uses mocked SDK/network boundaries, never live Stripe. Existing code handles checkout.session.completed; invoice/subscription update/cancellation event handlers were not implemented previously and are not introduced here. Existing subscription records and Stripe IDs are not deleted or migrated.

Payment cannot create a school, employee, account, school membership, role or activation. StripeProvisioningService now requires an existing non-archived staff profile/account, the exact recorded checkout session on its intent, and the exact customer/subscription/price already stored on that account. Conflicting or partly adopted canonical account/profile School IDs fail closed. Legacy name-only accounts may confirm only their exact already-established billing association; this does not establish canonical tenant authorization. No receipt or A7 activation setting changes.

The conditional billing update matches account/customer/subscription and enabled != false, preserving REPS's existing enabled-default compatibility. It only confirms paid/status/time; it cannot replace IDs, prices, ownership, roles, passwords, enabled state or profile data. Disabled pending accounts may finish recording an already-matching intent without being activated or receiving a billing update. An unmatched, new or unreviewed paid checkout fails before account/profile writes and remains retryable; it is not silently acknowledged as successfully provisioned. REPS must separately review outstanding sessions and resolve customer communication/refund/cancellation through its controlled billing process, not an automatic application side effect.

## Later controlled billing

Require a separately approved policy and implementation: independently approved existing school and account; canonical account/profile/School agreement; authorized billing actor; server-selected products/prices; server-persisted immutable tenant/account/session intent; explicit customer/subscription association; idempotent signed callbacks which cannot change membership or activation; onboarding/invitations kept separate from payment. Remove the hard stop only in a reviewed release with security-chain, Mongo, duplicate callback and mismatch tests. Do not expose the retained private builder as a shortcut or add a public operator flag.

## Deployment and rollback

Backend retirement is independent of inactive A7 preparation and can deploy before the companion frontend messaging. No environment variables, secrets, schema backfill or deployed data changes are required. Frontend preserves old return routes for existing links. Rolling back the backend would reopen public checkout and paid-account provisioning; prefer a forward fix while retaining the hard stop. No automatic merge, deployment, external subscription change or data mutation is performed by this PR.
