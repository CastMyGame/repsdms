# A7 Phase 4A: canonical core-workflow preparation

Backend baseline: dev 2e661f3 after merged PR #179. Frontend inspected at dev c302615. No deployed record inspection, ownership mapping, backfill, cloud-resource change or live send occurred.

## Inactive deployment boundary

CanonicalCoreWorkflows is registered only when the property `reps.tenancy.core-preparation-enabled=true` is explicitly supplied; it is absent by default. No application properties/deployment defaults are changed, no production controller/worker invokes it, and no new production endpoint exists. The existing false-only `reps.tenancy.id-enforcement-enabled` guard remains unchanged. Enabling the preparation bean is not ID-only cutover and cannot secure existing routes. Keep it absent/false in deployed environments; true is used only in the isolated tests here.

This adapter never calls WorkflowAccessService, UserContextService, AssignmentResolver or a legacy name-authorizing service. It reuses CanonicalAccountContext, so authenticated membership derives from current persisted account/profile IDs, roles, enabled/setup/archive state and versioned REPS identity. No caller-provided actor or school field establishes authority. Existing school names remain unchanged for display and compatibility in current routes.

## Canonical adapter contract

- Every actor comes from CanonicalAccountContext. Active students are queried by `_id + tenantSchoolId + archived != true`; the student account must exist uniquely in that tenant, be enabled and have only STUDENT role. Pending password setup does not prevent staff from issuing work to a newly provisioned student, but that account cannot authenticate into canonical context before setup.
- Student self-access requires matching persisted student profile ID. Staff additionally require current independent authority: ADMIN within tenant; GUIDANCE matching the student's recorded counselor; or TEACHER with the student email in persisted classes. Email comparisons preserve established case-insensitive reference semantics; tenant IDs are never normalized. Original case authorship and spotters alone cannot bypass a revoked underlying relationship.
- Case/detail queries include exact tenant ownership before related-student checks. No case ownership is inferred from a student's current school. Conflicting/moved/orphaned history stays stored and inaccessible for reviewed remediation. Archived case reporting is not implemented here.
- Guidance notes add participant restrictions; linked case/student agreement is checked. Roster validation verifies target staff account/profile and every student before returning an immutable list; teacher authority to edit their own class permits same-tenant enrollment without requiring that student to be in the roster already. It does not persist a roster.
- New-record preparation returns immutable server-derived tenant/actor/student metadata only. Any supplied actor/tenant/school claim is rejected, including matching display-name claims; future HTTP adapters must stop forwarding old identity fields. A selected student ID is a selector, never proof of access. OFFICE/GUIDANCE staff references come from the persisted student, not a supplied staff identifier.
- Notes/self-spotter updates use fixed server-generated fields with tenant/archival/profileRevision CAS and preserve currency/ownership. No arbitrary update operator, property name, collection or replacement document is accepted. Negative/stale revisions yield the existing generic HTTP 409. Entire batch validation finishes before any caller may attempt writes.
- Assignment guard validates ownership only; it does not validate completeness, assignment state, template precedence, question answers, command retries or review authorization. It uses an owner-scoped catalog predicate or an explicit system default (system flag, SYSTEM_DEFAULT, absent tenant and no staff/school owner). Snapshot ID must match the pinned case ID, and its owner must match or satisfy the same global exception. No alternate template substitution occurs.
- Returned Student/Documents are server-side inputs for future domain adapters, **not safe public response DTOs**. Current HTTP projection/privacy rules must be preserved when wiring them. Preparation metadata is not a reusable authorization token; relationships must be checked again at the actual commit boundary.

## Limits and Phase 4B sequencing

This is an independently testable preparation adapter with actual scoped Mongo operations; it is not a complete replacement for existing workflows. No canonical fields are added to case/template/binding/behavior models because their current replacement saves can remove or mutate ownership. Raw BSON ownership used in synthetic fixtures is not authorization to backfill those deployed collections.

Document-level note/spotter CAS is tested; cross-document role/roster/caseload reads are not a serializable authorization transaction. Concurrent relationship changes after validation and all-domain bulk transaction/idempotency semantics require a reviewed commit-boundary design before live activation. A successful prepareCreations/validateRoster return is not evidence of a saved record. No new case/recognition, assignment transition, currency debit/credit or notification intent is created by preparation. Existing production end-to-end behavior must be tested after its adapters are converted.

Phase 4B must:

1. Protect and adopt immutable ownership on every case/guidance/behavior/template/binding writer, including reminder and dormant legacy replacement paths. Keep retained case IDs, snapshots/answers/reviews, revisions and notification history intact.
2. Integrate canonical checks in actual factories, role-specific reads/mutations, archived history, account/provisioning/retirement, administrator spotter grants, roster CAS/enrollment and database-level lists/reports. Apply revision/relationship/owner conditions at the real write boundary, not only an earlier preflight.
3. Convert Positive Shout Out/redemption/reset execution only alongside the tested versioned legacy currency receipt bridge. Preserve existing receipt identifiers/payload hashes and transaction guarantees; never charge again because ownership metadata changed.
4. Convert durable notification capture/claims/background dispatch, Gmail grant owner binding and Stripe associations without resetting outcomes, rotating encryption or altering subscriptions. Validate related sender/recipient/account IDs; preserve failed/reconnect/uncertain recovery and action-ID semantics. No silent SMTP fallback or resend due to migration.
5. Coordinate frontend DTO/selector changes where legacy identity fields are removed, preserve names for presentation, and keep mobile/desktop error and action-ID behavior. No frontend change is needed merely to merge this disabled adapter.
6. Separately approve live inventory/provenance review, conditional pilot backfill and coherent account/profile/root coverage. Drain all incompatible instances and workers before data changes/cutover. Only a complete tenant-aware release may replace the global activation guard. No runtime ID/name fallback or partial route activation.

Rollback before backfill can remove this disabled module. After canonical backfill/cutover, retain IDs and use a tenant-aware binary, maintenance or reviewed forward correction; never roll back to name authority or overwrite new activity. See cutover-and-compatibility.md. This PR must not be used as a justification to activate production isolation or claim A7 closure.
